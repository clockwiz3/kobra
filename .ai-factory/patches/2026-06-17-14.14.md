# Порядок карточек в колонке не сохранялся: move не сдвигал соседей

**Date:** 2026-06-17 14:14
**Files:** app/Services/Kanban/CardService.php, tests/Feature/Couple/CardTest.php
**Severity:** medium

## Problem

После перетаскивания карточки (внутри колонки или между колонками) и
перезагрузки доски порядок карточек мог перетасоваться — «хранимый» порядок
не соответствовал тому, что пользователь собрал мышью.

## Root Cause

`CardService::move` делал ровно один апдейт:

```php
$card->update(['board_column_id' => $toColumnId, 'position' => $toPosition]);
```

Он выставлял `position` **только перемещаемой** карточки и не трогал соседей:

- В целевой колонке появлялись **дубли `position`** (например, два разных
  card с `position = 1`). Связь `BoardColumn::cards()` сортирует лишь
  `->orderBy('position')` — при равных position ничью разруливает БД (порядок
  вставки / id), а не индекс, куда пользователь бросил карточку. Поэтому после
  reload порядок «съезжал».
- В исходной колонке оставалась **дыра** в нумерации (ушла карточка с
  position=1 → осталось 0,2,3...), что копило коллизии при следующих move.

Контраст: `BoardService::reorderColumns` уже делал правильную переиндексацию
(`position = индекс` для каждого id) — для карточек этот паттерн просто забыли
применить при первичной реализации couple-scoped бэкенда (commit 0f9b7cf).

Фронтенд при этом двигал карточки оптимистично (локальный splice), поэтому в
рамках сессии всё выглядело корректно — расхождение всплывало только на reload
(fetchBoard), что маскировало баг.

## Solution

`move` переписан на контигуальную переиндексацию в транзакции:

1. Карточка относится к целевой колонке (`board_column_id`).
2. Берётся текущий порядок целевой колонки **без** перемещаемой карточки
   (`orderBy(position)->orderBy(id)`), карточка вставляется `array_splice` на
   запрошенный индекс (с клампом `max(0, min($pos, count))`).
3. Хелпер `renumber()` пишет контигуальные позиции `0..n-1` — это и есть
   «хранимый порядок».
4. При переезде между колонками так же компактится исходная колонка.
5. Всё в `DB::transaction` — промежуточные коллизии position не видны; возврат
   `refresh()`-нутой модели, чтобы `CardData.position` был каноничным.

Покрыто двумя feature-тестами (same-column reorder; cross-column insert +
compaction), проверяющими и порядок id, и контигуальность position после reload.

## Prevention

- Любая операция «положить элемент на индекс N в упорядоченном списке» обязана
  **переиндексировать соседей**, а не писать одну позицию. Один апдейт позиции
  без сдвига = гарантированные коллизии.
- Если в модели уже есть `orderBy('position')` без вторичного ключа — порядок
  при равных position недетерминирован; хранить позиции строго контигуально
  (0..n-1) и обновлять их транзакционно.
- Искать в проекте парные операции reorder/move: если одна (reorderColumns)
  переиндексирует, а вторая (move) нет — это рассинхрон-смелл.
- Тестировать порядок **после повторной выборки из БД** (reload), а не только
  ответ самой мутации — оптимистичный фронтенд маскирует серверный баг.
- Code review: для drag-and-drop persist смотреть, что сервер пишет позиции
  всем затронутым элементам обеих колонок (источник + приёмник).
